# Agent Note: 外观变化期间由持久化皮肤保持所有权

Status: implemented

[English](2026-08-24-persistent-skin-ownership-during-appearance-changes.md) | 中文

## 问题

浏览器表面会把选中的 Oh-DSH 皮肤持久化到共享的 `skins.json`，但主题运行时在 Host 外观设置加载期间也会发布内置的 `light`、`dark` 或 `system` snapshot。皮肤控制器把每个内置 snapshot 都当成用户要求退出当前皮肤，并删除 `activeId`。因此，已保存皮肤可能先在启动期间生效，又在较晚完成的设置读取到达后消失；前一次写入虽然成功，下一次启动仍回到原始外观。

同一种事件同时承载启动期加载和用户显式外观切换。上游主题服务没有公开事件来源或 readiness handle，所以下游皮肤代码无法据此区分两者。

## 决策

只要 `skins.json` 中存在有效的 `activeId`，它就持续保持权威，直到皮肤所有者主动删除它。控制器在仍有有效已保存皮肤时收到内置主题 snapshot，会把该内置偏好记录为 `fallbackTheme`，重新应用已保存皮肤，并保持皮肤 snapshot 与 DOM 呈现。无效的已保存 ID 仍会被删除。

选择**原始外观**是退出皮肤的显式操作。`setSkin(null)` 会先删除 `activeId`，再应用 `fallbackTheme`；因此随后产生的内置 snapshot 已没有可恢复的皮肤，控制器会清除皮肤呈现。皮肤仍激活时，选择浅色、深色或跟随系统只更新原始外观之后要显示的回退值，不再隐式删除皮肤。

这条规则让皮肤身份和持久化继续归 `@oh-dsh/skins` 所有。上游主题服务仍拥有内置外观偏好及其 Host 设置文档。

## 考虑过的替代方案

**恢复皮肤之前等待第二个 `ui-theme` settings scope。** 每次绑定都会独立发起 Host 读取。一个 scope 可能先于主题运行时的私有 scope 进入 ready，因此它不是同步屏障，较晚的主题读取仍可能清除皮肤。

**只忽略第一次内置主题事件。** 事件没有来源字段，Host 加载可能很晚才发生，也可能在重连后发生多次。按顺序抑制既可能丢弃真实用户选择，也可能漏掉更晚的加载。

**在固定延时之后重新应用皮肤。** 设置与重连延迟不存在稳定的产品上限。定时器只会移动竞态。

**把皮肤保存到浏览器 localStorage。** Desktop 和 Web 的端口可能变化，第二套存储还会与所有 Oh-DSH 表面共用的 `skins.json` 分叉。

**让上游主题设置 schema 接受自定义皮肤 ID。** 这会把皮肤身份所有权从 `@oh-dsh/skins` 转移出去，并要求修改 DSH runtime contract。下游所有者无需扩大上游 schema 就能保证持久化。

## 后果

已保存皮肤可以跨启动期加载、延迟 Host 读取和后续内置主题发布继续保留。用户通过皮肤列表中的“原始外观”退出皮肤；皮肤激活期间的外观选择只配置回退值，不会替换皮肤。

控制器可能在重连触发的外观刷新后再次应用同一个已保存皮肤。对于已经选中的 ID，主题注册与应用是幂等的；偏好存储也会合并未变化的写入。

`tests/skins.test.ts` 覆盖从磁盘恢复之后才到达的外观加载、皮肤保持激活时的回退更新，以及显式选择原始外观后的清除行为。打包后的 Windows runtime 还会通过完整的选择、退出、重启和延迟观察闭环进行验证。
